# T-Retro

T-Retro является внутренним веб-приложением для ретроспектив IT-команд. Сотрудник создаёт доску и приглашает команду, после чего участники собирают карточки, группируют их, голосуют за темы и фиксируют итоги обсуждения. Результатом встречи являются решения, комментарии, задачи и PDF по постоянному адресу.

Интерфейс и отчёт используют русский язык. Проект находится на этапе подготовки к разработке, поэтому сейчас репозиторий содержит документацию и не содержит исходный код приложения.

## Локальный MVP

MVP должен позволить нескольким тестовым сотрудникам пройти полную встречу в двух независимых браузерных контекстах. В него входят следующие возможности:

- личные и общие шаблоны, создание встречи, приглашения и управление участниками;
- присутствие, передача и перевыборы фасилитатора, синхронизация через SignalR;
- сбор карточек с настройками приватности, готовность и переходы фаз;
- ручная группировка, порт предложений ИИ и тестовый адаптер;
- голосование, очередь обсуждения, решения, комментарии и задачи;
- общий таймер, тестовый экспорт Jira, завершение встречи и сохранённый PDF.

Локальное хранение MVP использует SQLite в файле. Для работы SQLite не нужен отдельный сервер БД. PostgreSQL остаётся целевой СУБД итоговой поставки, а его реализация и проверки находятся в [этапе P1](docs/tasks.md#этап-p1-postgresql-для-итоговой-поставки).

В MVP не входят production-адаптеры TWork, Jira, внутреннего ИИ и Sage. Kubernetes, GitLab CI и нагрузочная приёмка также отложены до этапов итоговой поставки.

## Отдельные решения по требованиям

Таймер хранится только в памяти процесса. БД не содержит его состояние, `runId`, срок окончания или дедупликацию команд. После перезапуска приложения таймер отсутствует, и старый звуковой сигнал не воспроизводится.

Решения и комментарии являются разными сущностями. Фасилитатор управляет обеими сущностями во время `Discuss`, а после `Closed` их содержимое фиксируется. В PDF решения и комментарии выводятся отдельно.

Сотрудник, который вступил во время `Vote`, получает полный текущий бюджет голосов. Вступление не меняет число исходных карточек и бюджет остальных участников.

## Целевая архитектура

Backend использует .NET 10, C# 14, ASP.NET Core, SignalR и Dapper. Итоговая реализация хранения использует Npgsql и PostgreSQL, а временная локальная реализация использует `Microsoft.Data.Sqlite`. Frontend использует Angular и Taiga UI 4.x.

| Проект | Назначение |
| --- | --- |
| `Domain` | Правила фаз, групп, голосования и доменные модели. |
| `Application` | Сценарии, права, персональная видимость и порты хранения и интеграций. |
| `Infrastructure` | SQL, миграции, Dapper, PDF, фоновые операции и адаптеры. |
| `Api` | HTTP DTO, OpenAPI, SignalR, личность и настройка зависимостей. |
| `web` | Angular SPA, экраны и клиенты HTTP и SignalR. |

Проекты и зависимости должны соответствовать [§10 спецификации](docs/Retro_Spec.md#10-архитектура-и-границы-данных). Точные версии frontend и lock-файл будут зафиксированы в задаче M0.2 после проверки совместимости. Нельзя использовать `force` или `legacy-peer-deps` для установки несовместимых пакетов.

Первая поставка рассчитана на один процесс приложения и один pod. Присутствие и таймер находятся в памяти, поэтому горизонтальное масштабирование требует отдельного проектирования.

## Запуск

Сейчас приложение запустить нельзя, потому что исходный код ещё не создан. Основа запуска реализуется в [этапе M0](docs/tasks.md#этап-m0-основа-локального-mvp).

После завершения M0 в этом разделе будут указаны следующие сведения:

- требуемые версии .NET SDK, Node и менеджера пакетов;
- команды чистой установки, миграций, запуска API и Angular;
- параметры строки подключения SQLite и расположение файла БД;
- способ входа под несколькими тестовыми сотрудниками;
- команды production build и тестов.

Для итогового запуска потребуется внешний PostgreSQL. Сервер PostgreSQL не входит в поставку. Настройки production не должны молчаливо переключать приложение на SQLite или тестовую личность.

## Конфигурация и интеграции

Конкретные имена переменных и примеры конфигурации будут добавлены вместе с кодом. Секреты должны передаваться извне и не попадать в репозиторий.

TWork, Jira, внутренний ИИ и Sage подключаются через отдельные порты. Для локального сценария создаются тестовые адаптеры. Корпоративные адреса, заголовки и схемы аутентификации нужно получить из соответствующего окружения, а не выдумывать.

Production должен отклонять тестовую личность. Отсутствие настроек ИИ или Jira отключает только соответствующее действие и не должно мешать базовой встрече и readiness probe.

## Проверка

Правила и персональная приватность проверяются отдельно от Angular. Интеграционные тесты MVP выполняются с реальным SQLite, а общий сценарий проходит минимум в двух независимых браузерных контекстах.

Успешные тесты на SQLite не подтверждают поведение PostgreSQL. Миграции, составные ограничения, блокировки, конкурентные команды и физическое удаление приватных связей нужно отдельно проверить на PostgreSQL в итоговой поставке.

Текущий статус проверок: сборка и тесты ещё не выполнялись, поскольку код отсутствует. Команды и фактические результаты будут добавлены по мере выполнения [этапа M10](docs/tasks.md#этап-m10-проверка-mvp) и [этапа P4](docs/tasks.md#этап-p4-итоговая-приёмка).
