# T-Retro

T-Retro является внутренним веб-приложением для ретроспектив IT-команд. Сотрудник создаёт доску и приглашает команду, после чего участники собирают карточки, группируют их, голосуют за темы и фиксируют итоги обсуждения. Результатом встречи являются решения, комментарии, задачи и PDF по постоянному адресу.

Интерфейс и отчёт используют русский язык. Реализованы этапы с M0 по M9: основа приложения, встречи, приглашения, SignalR, роль фасилитатора, карточки, приватность, готовность, группировка, голосование, обсуждение, таймер, mock-экспорт задач в Jira, завершение встречи и PDF. Следующим этапом является M10 с итоговой проверкой локального MVP. Внутренний ИИ и Jira пока представлены локальными заглушками без сетевых вызовов.

## Локальный MVP

MVP позволяет нескольким тестовым сотрудникам пройти полную встречу в независимых браузерных контекстах. Запуск через `tools/run.sh` по умолчанию использует файл SQLite. Запуск через Compose использует PostgreSQL 18. Статус проверки на внешней базе указан в [этапе P1](docs/tasks.md#этап-p1-postgresql-для-итоговой-поставки).

В MVP не входят production-адаптеры TWork, Jira, внутреннего ИИ и Sage. Kubernetes и нагрузочная приёмка отложены до этапов итоговой поставки. Сборка и тесты уже запускаются в GitHub Actions.

Таймер хранится только в памяти процесса. Отсчёт и сообщение об истечении показываются в верхней панели без звука. БД не содержит его состояние, `runId`, срок окончания или дедупликацию команд. Решения и комментарии являются разными сущностями. Сотрудник, который вступил во время `Vote`, получает полный текущий бюджет голосов.

После выбора шаблона можно просмотреть и изменить колонки, назвать ретро и открыть отдельные настройки видимости и голосования. Кнопка «Создать ретро» сохраняет настройки и открывает доску сбора. Название встречи и кнопка «Пригласить» находятся рядом с логотипом. Окно приглашения показывает ссылку и QR-код. Если получатель ещё не вошёл, после входа открывается подтверждение вступления, а затем текущий этап встречи.

Значок слева от аватаров открывает список участников. Фасилитатор может там пригласить сотрудника, передать роль или исключить участника. На этапах сбора, группировки и голосования аватары готовых участников отмечены галочкой. Рядом с «Я готов» виден счётчик `X/Y`, а при неполной готовности интерфейс просит фасилитатора подтвердить переход.

При группировке карточки перетаскивают на другую карточку, группу или свободное место колонки. Группы можно переименовывать, сворачивать и переносить за заголовок. Миграция `0013_card_original_column_color.sql` хранит исходный цвет карточки. Для существующих карточек записывается цвет их колонки на момент миграции.

Голосование проходит на доске. У каждой одиночной карточки и группы участник видит только число своих голосов в формате «− 4 +». Общая сумма по теме открывается на этапе обсуждения. Личный остаток показан рядом с этапами. Фасилитатор меняет число голосов на человека в окне у таймера. При отключённом голосовании встреча переходит от группировки сразу к обсуждению, все темы получают ноль голосов. Эту настройку хранит миграция `0012_optional_voting.sql`.

При обсуждении слева виден список тем по голосам, справа открывается выбранная тема. Каждый участник может открыть любую тему у себя. Выбор фасилитатора открывает тему у всех. Кнопка «Далее» отмечает текущую тему обсуждённой и открывает следующую по списку. Кнопка «Пропуск» сохраняет отметку «Пропущена» и открывает следующую тему, если она есть.

Комментарии и задачи участников появляются в общей ленте темы вместе с решениями фасилитатора. Для задачи требуется краткое название. Описание и исполнителя можно заполнить по желанию. Миграция `0014_discussion_feed.sql` добавляет хранение описания и порядка записей.

На этапе итогов кнопки «Скачать PDF» и «Скачать JSON» находятся рядом с дорожкой этапов. На доске видны голоса и число записей по каждой теме. Кнопка записей открывает справа ленту для чтения. Темы, которые не успели обсудить, выделены бледным цветом.

Фасилитатор может архивировать ретро на любом этапе. Встреча исчезает из недавних и остаётся на текущем этапе. Участники могут продолжить встречу по ссылке на доску и скачать PDF после её завершения. На главной список архивных встреч загружается при раскрытии раздела «Архив ретро». Миграция `0015_meeting_archive.sql` добавляет дату архивирования.

## Архитектура

Backend использует .NET 10, C# 14, ASP.NET Core и Dapper. Для SQLite используется `Microsoft.Data.Sqlite`, для PostgreSQL используется Npgsql. У каждой СУБД своя схема миграций. Frontend использует Angular и Taiga UI 4.x.

| Проект | Назначение |
| --- | --- |
| `src/Domain` | Правила и доменные модели. |
| `src/Application` | Сценарии, права и порты хранения и интеграций. |
| `src/Infrastructure` | SQL, миграции, Dapper, PDF и адаптеры. |
| `src/Api` | HTTP DTO, OpenAPI, SignalR, личность и composition root. |
| `web` | Angular SPA, экраны и клиенты HTTP и SignalR. |
| `tests` | Domain, Application, Infrastructure и API-тесты. |

Решение находится в `TRetro.slnx`. Зависимости между проектами соответствуют [§10 спецификации](docs/Retro_Spec.md#10-архитектура-и-границы-данных).

## Завершение и PDF

В SQLite и PostgreSQL одна транзакция сохраняет итоги и PDF, удаляет приватные связи, очищает готовность, закрывает приглашение и переводит встречу в `Closed`. Ошибка генерации откатывает всю операцию. Повтор исходной команды возвращает тот же сохранённый отчёт.

При закрытом сборе чужие карточки видны только как заглушки в колонках. После сбора открываются тексты. Общая анонимность встречи или выбор «Анонимно» при создании карточки скрывает её автора. Миграция `0011_card_anonymity.sql` сохраняет выбор анонимности. При завершении удаляются связи с авторами анонимных карточек и соответствующие записи создания.

Индивидуальные голоса и версии бюллетеней удаляются при завершении при любых настройках. Суммы по темам, членство для проверки доступа и назначения исполнителей сохраняются.

Миграция `0010_column_descriptions.sql` добавляет необязательные описания колонок встреч и шаблонов. Описания сохраняются при создании встречи из шаблона и видны на доске.

`GET /api/meetings/{id}/report.pdf` при каждом запросе проверяет личность и действующее членство. Все допущенные участники получают одинаковые байты с `application/pdf` и `Cache-Control: private, no-store`. После завершения состояние читается из сохранённых итогов; готовность и личный бюджет не выдаются. Экспорт задачи в mock Jira остаётся доступным в `Closed` и не перегенерирует PDF.

`GET /api/meetings/{id}/report.json` после завершения отдаёт файл `retro-results.json` с `application/json` и `Cache-Control: private, no-store`. Действующие участники получают одинаковые данные из сохранённых итогов. Файл содержит название и даты встречи, счётчики, колонки, темы в порядке обсуждения, карточки, суммы голосов, статусы, комментарии, решения и тексты задач. В JSON отсутствуют список участников, авторство, исполнители, идентификаторы пользователей и личные голоса при любых настройках встречи. Сохранённый текст выгружается целиком, включая имена, вписанные вручную.

PDF генерируется локально через PDFsharp без сетевых вызовов. Шрифты DejaVu Sans Regular и Bold с кириллицей встроены в приложение и PDF. Длинные тексты переносятся, страницы нумеруются. Лицензии находятся в [PDFsharp-LICENSE.txt](src/Infrastructure/Reporting/PDFsharp-LICENSE.txt) и [DejaVu-LICENSE.txt](src/Infrastructure/Reporting/Fonts/DejaVu-LICENSE.txt).

## Скрипты macOS и Ubuntu

Из корня репозитория запустите:

```bash
./tools/build.sh
./tools/run.sh
```

`tools/build.sh` поддерживает macOS и Ubuntu Linux. Он проверяет ОС, точную версию .NET SDK из `global.json` и мажорные версии Node.js и npm из `.nvmrc` и `web/package.json`. Затем выполняет restore, чистую сборку и тесты backend, `npm ci`, production build, unit-тесты frontend и все E2E. Playwright Chromium устанавливается в `.tools/playwright`. На Ubuntu системные зависимости устанавливаются через `playwright install --with-deps chromium`. E2E используют отдельную SQLite в `.tools/e2e`. Скрипт совместим с системным Bash 3.2 и не требует Docker.

`tools/run.sh` требует предварительного успешного `tools/build.sh`, применяет миграции и одновременно запускает API на `http://127.0.0.1:5166` и Angular на `http://127.0.0.1:4200`. Нажатие Ctrl+C останавливает оба процесса. Рабочая база остаётся в `src/Api/data/t-retro.db`.

При локальном запуске через `ng serve` SignalR подключается напрямую к API на порт 5166. CORS с credentials разрешён только для `localhost:4200` и `127.0.0.1:4200`; Vite проксирует HTTP `/api`, `/health` и `/openapi`, но не выступает WebSocket-прокси. При закрытии страницы приложение останавливает SignalR через `pagehide`. Собранный Angular подключается к SignalR по тому же адресу, на котором открыта страница.

При открытии встречи доска загружается по HTTP параллельно с подключением SignalR. Если WebSocket не открывается за 4 секунды, SignalR пробует запасной транспорт. Команды становятся доступны после подписки и свежего снимка встречи.

Для push и pull request GitHub Actions запускает `tools/build.sh` на `ubuntu-latest` x86_64. В workflow добавлен второй прогон API и Playwright с отдельным сервисом PostgreSQL 18. Проверку конкретного коммита можно найти по его SHA. [Конфигурация CI](.github/workflows/ci.yml)

## Запуск через Docker Compose

[Dockerfile](Dockerfile) собирает Angular и ASP.NET Core в одном образе. Angular размещается в `wwwroot`. ASP.NET Core отдаёт страницы, API и SignalR на одном порту. [Compose](docker-compose.yml) запускает одноразовую команду `--migrate`, затем приложение. Приложение доступно с хоста на `http://127.0.0.1:8080`.

Запустите Docker и выполните из корня проекта команду:

```sh
./tools/run-postgres.sh
```

Скрипт использует `POSTGRES_PASSWORD` из окружения или из `.env`. Если ни переменной, ни файла нет, скрипт генерирует пароль и сохраняет его в локальный `.env`. Если файл уже существует, укажите пароль в нём или в окружении. Скрипт ждёт готовности приложения и завершает работу, а контейнеры продолжают работать.

Compose запускает приложение в `Development` с локальным входом. Приложение использует сервис `postgres` по адресу `postgres:5432`. Имя базы и пользователя одинаковое, `t_retro`. Именованные тома хранят данные PostgreSQL и ключи сессий. Встречи из старой SQLite доступны через `./tools/run.sh`.

Сервис миграций ждёт успешной проверки `pg_isready`. Приложение запускается после завершения миграций, а `/health/ready` проверяет доступность PostgreSQL и версию схемы. Посмотреть состояние сервисов можно через `docker compose ps`. Остановить их с сохранением томов можно через `docker compose down`.

Для Kubernetes проект рассчитан на один pod с одним контейнером приложения. PostgreSQL предоставляется отдельно. [Эксплуатация и health endpoints](docs/operations.md). [Модель pod в Kubernetes](https://kubernetes.io/docs/concepts/workloads/pods/).

## Ручной запуск

Выполните миграции из корня репозитория:

```bash
dotnet restore TRetro.slnx
dotnet run --project src/Api --launch-profile http -- --migrate
```

По умолчанию команда создаёт `src/Api/data/t-retro.db`. Для внешнего PostgreSQL задайте `Database__Provider=PostgreSQL` и передайте строку подключения через `ConnectionStrings__Default` при миграции и при запуске. Повторный запуск миграций безопасен для обеих СУБД.

Запустите API:

```bash
dotnet run --project src/Api --launch-profile http
```

API доступен на `http://localhost:5166`. OpenAPI находится на `http://localhost:5166/openapi/v1.json`.

В другом терминале запустите Angular:

```bash
cd web
npm ci
npm start
```

Откройте `http://localhost:4200`. Для локального входа можно использовать `employee-a` и `Сотрудник А`. Во втором независимом браузерном профиле нужно использовать другой subject, например `employee-b`. Angular проксирует `/api`, `/health` и `/openapi` на порт 5166.

Проверки процесса доступны без входа:

- `GET /health/live` проверяет процесс без обращения к БД.
- `GET /health/startup` подтверждает запуск приложения.
- `GET /health/ready` проверяет БД и последнюю версию схемы.

## Конфигурация

Основные параметры находятся в `src/Api/appsettings.json` и переопределяются стандартными переменными ASP.NET Core:

- `Database__Provider` принимает `SQLite` или `PostgreSQL`.
- `ConnectionStrings__Default` задаёт строку подключения выбранной СУБД. Для PostgreSQL укажите `Host`, `Database` и `Username`. Пароль можно передать через `PGPASSWORD`, как в Compose.
- `DevAuthentication__Enabled` включает локальный вход только в Development и Testing.
- `Integrations__Ai__Enabled` включает локальную заглушку предложений группировки. В Development и Testing она включена по умолчанию, в основном конфиге выключена. Адрес и ключ внешнего сервиса не используются.
- `Integrations__Jira__Enabled` включает mock Jira. В Development и Testing она включена, в основном конфиге выключена. `Integrations__Jira__Outcome` задаёт исход `Created`, `Rejected`, `Unknown` или `Unavailable`; `Integrations__Jira__DelayMs` имитирует задержку ответа. Сетевые вызовы не выполняются.

В production разрешена команда миграции PostgreSQL. Для запуска веб-приложения в production требуется реализация TWork. Секреты передаются через внешнюю конфигурацию.

## Сборка и тесты

Backend:

```bash
dotnet restore TRetro.slnx
dotnet build TRetro.slnx --no-restore
dotnet test TRetro.slnx --no-build --no-restore
```

Frontend:

```bash
cd web
npm ci
npm run build
npm test -- --watch=false
```

Для браузерных проверок M1–M9 нужно один раз установить Chromium и затем запустить сценарии:

```bash
cd web
PLAYWRIGHT_BROWSERS_PATH=../.tools/playwright npx playwright install chromium
npm run test:e2e
```

Для проверки PostgreSQL после сборки задайте строку подключения к отдельной тестовой базе в `TRETRO_TEST_POSTGRES`. Пользователь тестовой БД должен иметь право создавать схемы. API-тесты создают и удаляют собственные временные схемы. Браузерные тесты применяют миграции и записывают встречи в схему из переданной строки подключения.

```sh
dotnet test tests/Api.Tests/Api.Tests.csproj --no-build --no-restore --verbosity minimal
(cd web && TRETRO_E2E_POSTGRES="$TRETRO_TEST_POSTGRES" npm run test:e2e)
```

На SQLite прошли 87 backend-тестов (Domain 25, Application 10, Infrastructure 7, API 45), 11 тестов Angular и 9 браузерных сценариев. На отдельном PostgreSQL 18 прошли 45 API-тестов и те же 9 браузерных сценариев. Сценарий завершения скачивает PDF и JSON с доски итогов. Приёмочный прогон ждёт доступ к внешней базе из P1.5.

API-тесты M3 проверяют все сочетания флагов приватности в необработанном JSON, права автора, версии, идемпотентность команд и строки SQLite. Проверки M4 покрывают инварианты групп, конфликты версий доски, ручной перенос после предпросмотра и отключённую заглушку. Миграция `0006_voting.sql` добавляет темы, голоса и личные бюллетени. Проверки M5 покрывают 41 исходную карточку и 32 темы, бюджет 3, позднее вступление, приватность бюллетеней и общие суммы после голосования, исключение и гонки команд. Миграция `0007_discussion.sql` добавляет очередь, текущую тему, комментарии, решения и задачи в раздельных таблицах. Проверки M6 покрывают рейтинг 2, 2 и 0, выбор темы в двух браузерных сессиях, создание комментариев и задач участниками, порядок ленты и сохранение исторических назначений. Таймер M7 не добавляет миграций или записей в БД: состояние, `runId` и дедупликация находятся только в памяти. Проверки M7 покрывают идемпотентность, истечение, отмену, рестарт, reconnect и визуальное сообщение об истечении. Миграция `0008_jira_exports.sql` добавляет намерения и исходы mock-экспорта. Проверки M8 покрывают постоянный `externalRequestId`, один mock-POST при повторах и гонках, блокировку задачи, успех, отказ, недоступность, потерю ответа и порт сверки.

Проверки M9 покрывают оба значения `anonymousCards`, удаление индивидуальных голосов, сохранённые итоги и строки SQLite, физическое удаление связей и записей создания карточек, нулевые темы, решения, комментарии, задачи и назначения. Отдельно проверяются откат при ошибке PDF, повтор и конфликт команды, пустое ретро, доступ участника из новой сессии, запрет постороннему и исключённому, одинаковые байты PDF, кириллица и многостраничная карточка. [CompletionApiTests](tests/Api.Tests/CompletionApiTests.cs) открывает реальные PDF через PdfPig, а [M9 E2E](web/e2e/m9.spec.ts) проходит весь маршрут в двух браузерных контекстах.

`npm audit` сообщает о четырёх предупреждениях в цепочке `ng-morph` и `minimatch`, которая относится к optional-зависимостям схем Taiga UI. Совместимость возможного исправления ещё предстоит проверить. Исследование остаётся задачей M10.8.
