# AGENTS.md

Файл содержит правила для агентов и разработчиков, которые меняют этот репозиторий. Перед началом работы нужно прочитать [handoff](docs/handoff.md), [техническое задание](docs/Retro_Spec.md), выбрать задачу в [плане реализации](docs/tasks.md) и проверить актуальный статус проекта в [README.md](README.md).

## Сохранение контекста между сессиями

По запросу пользователя `сохрани сессию` или `bfe` нужно обновить [docs/handoff.md](docs/handoff.md). Тот же порядок применяется к любой явной просьбе сохранить контекст перед началом новой сессии.

Перед обновлением нужно проверить фактическое состояние файлов, статусы задач, последние команды и их результаты. Handoff должен содержать текущее состояние, выполненные работы, текущую незавершённую работу, следующие действия, блокировки, принятые решения, результаты проверок и ссылки на все нужные файлы. Нельзя ограничиваться коротким резюме диалога или оставлять устаревшие сведения.

При сохранении сессии нужно проверить спецификацию, план, README, этот файл и handoff на непротиворечивость, полноту и актуальность. Найденные расхождения нужно исправить. Если исправление требует нового решения пользователя, расхождение и вопрос нужно явно записать в handoff.

В начале новой сессии нужно сначала прочитать handoff, а затем сверить его с фактическим состоянием проекта. Нельзя считать снимок актуальным только потому, что он был сохранён ранее.

## Приоритет решений

Основным источником требований является [техническое задание](docs/Retro_Spec.md). Решения ниже уточняют документ и имеют приоритет в местах, где старый текст противоречит им.

- Таймер полностью хранится в памяти процесса. В БД запрещено сохранять состояние таймера, `endsAtUtc`, `runId` и записи дедупликации его команд. После рестарта приложения таймер отсутствует, старый сигнал не воспроизводится.
- Решения и комментарии являются разными сущностями. Для каждой сущности нужны свои хранение, API и представление в итогах и PDF.
- Сотрудник, вступивший во время `Vote`, получает полный текущий бюджет. Число исходных карточек и бюджет остальных участников не пересчитываются.
- Локальный MVP использует SQLite и включает полную встречу до `Closed` и PDF. PostgreSQL остаётся целевой СУБД итоговой поставки.
- Проверки на SQLite не подтверждают PostgreSQL-специфичные требования. Такие проверки нужно оставить открытыми в [плане](docs/tasks.md).
- Внутренний ИИ пока заменён локальной заглушкой за портом `IGroupSuggestionProvider`. Она не выполняет сетевые вызовы и не имитирует корпоративный контракт. Ручная группировка должна работать при отключённой заглушке.

При изменении этих решений нужно обновить данный файл, спецификацию, план и README в рамках той же работы.

## Архитектура

Целевой backend использует .NET 10, C# 14, ASP.NET Core, SignalR, Dapper, Npgsql и PostgreSQL. Временный SQLite-адаптер использует Dapper и `Microsoft.Data.Sqlite`. Frontend использует Angular и Taiga UI 4.x. Версии Angular и связанных пакетов нужно выбирать по совместимости peer dependencies и фиксировать в lock-файле. Запрещено использовать `force` или `legacy-peer-deps` для обхода конфликтов.

Проект разделён на `Domain`, `Application`, `Infrastructure`, `Api` и `web` согласно [§10 спецификации](docs/Retro_Spec.md#10-архитектура-и-границы-данных).

- `Domain` содержит правила и модели без атрибутов хранения и сериализации.
- `Application` содержит сценарии, проверки прав, персональную видимость и порты. Слой зависит только от Domain.
- `Infrastructure` содержит SQL, Dapper, миграции, PDF, адаптеры интеграций и фоновые операции.
- `Api` содержит HTTP DTO, SignalR, установление личности и composition root.
- `web` обращается к backend только через публичный контракт.

Каждый внешний слой имеет собственные типы. Нельзя создавать общий сквозной `CardDto` или передавать строки БД в Application и Angular. Мапперы должны быть явными и ручными на границах слоёв. Dapper и SQL допустимы только в Infrastructure, все значения SQL должны быть параметризованы.

Разные диалекты SQLite и PostgreSQL нужно изолировать за портами. Нельзя переносить `SELECT ... FOR UPDATE`, `timestamptz` или `bytea` в SQLite-миграции и нельзя ослаблять PostgreSQL-схему ради общего SQL.

## Правила предметной области

- Переходы фаз идут только на одну фазу вперёд. Сервер проверяет исходную фазу, членство, роль и версии при каждой команде.
- Изменения одной команды встречи атомарны. Конфликты версий не должны приводить к частичной записи.
- Группа содержит не менее двух карточек и имеет один уровень вложенности. Голосование и обсуждение работают с темой, а не с карточкой внутри группы.
- Все команды таймера идемпотентны только в пределах текущего процесса. При рестарте его состояние и история команд исчезают.
- Присутствие и соединения можно хранить в памяти одного процесса. Срок и поколение ожидающего перевыбора фасилитатора сохраняются в БД.
- До получения отдельного решения приложение рассчитано на один процесс и один pod. Нельзя заявлять поддержку горизонтального масштабирования.
- На текущей машине Docker отсутствует. Dockerfile и docker-compose можно создавать на этапе P3, но нельзя использовать Docker для локальных проверок или выдавать такие проверки за выполненные.

## Приватность и завершение

Персональная фильтрация выполняется на сервере. Скрытые текст, автор и связи с автором нельзя включать в HTTP, HTML, общие события SignalR, метаданные PDF или логи. Нельзя полагаться на скрытие полей только в Angular.

При завершении нужно физически удалить связи карточек с авторами при `anonymousCards=true` и индивидуальные голоса при `anonymousVotes=true`. Флаги проверяются независимо. Нельзя создавать служебную историю, из которой приложение сможет восстановить удалённые связи.

В логи запрещено писать тексты карточек, комментариев, решений и задач, тела запросов, токены, полные ссылки приглашений, расклады голосов, связи авторов и сырые ответы внешних систем.

## Интеграции и конфигурация

TWork, Jira, внутренний ИИ и Sage подключаются через порты Application. До получения корпоративных контрактов реализуются тестовые адаптеры и конфигурация отключения. Нельзя придумывать корпоративные URL, заголовки, имена пакетов или схемы аутентификации.

Тестовая личность допустима только в Development и тестах. Production должен отклонять небезопасную конфигурацию. Отсутствие настроек ИИ или Jira отключает только соответствующее действие и отображается в UI.

Секреты передаются через внешнюю конфигурацию. Нельзя добавлять их в репозиторий, логи или документацию.

## Порядок работы

1. Выбрать незавершённую задачу в [docs/tasks.md](docs/tasks.md) и сверить её со спецификацией.
2. Реализовать изменение вместе с проверками основных правил и ошибок. Не расширять объём без отдельной задачи.
3. Выполнить доступные стандартные команды сборки и тестов, а также пользовательский сценарий, затронутый изменением.
4. Отметить задачу выполненной только после успешной проверки. Если проверка невозможна, записать причину рядом с задачей и в README.
5. Обновить README при изменении команд, конфигурации, версий или границ запуска. Обновить этот файл при изменении описанных здесь правил.

Нельзя помечать всю задачу выполненной, если реализована только её часть. Нельзя выдавать успешный запуск на SQLite за итоговую приёмку PostgreSQL или production-интеграций.

## Проверки перед завершением

- Domain-правила и персональная приватность проверяются независимо от Angular.
- Интеграционные проверки выполняются на реальной выбранной СУБД, а не только на моках хранилища.
- Пользовательский маршрут проверяется минимум в двух независимых браузерных контекстах, когда изменение затрагивает совместную работу.
- Для завершения встречи проверяются сохранённые строки, физическое удаление связей и фактические байты PDF.
- На macOS полный локальный цикл выполняется через `tools/build`, а запуск приложения — через `tools/run`. Тот же `tools/build` используется в GitHub Actions из `.github/workflows/ci.yml`.
- После сборок и тестов нужно проверить `git status` и удалить только созданные проверками ненужные файлы.

Ссылки на материалы по версиям и технологиям находятся в [README.md](README.md#материалы-по-технологиям).
